## Queue, count, detail and recency

Scheduling chip scope is period-wide before toolbar person/work-role/job/customer/status filters, as current code implements. Pass this scope explicitly; contextual chips pass their booking/job/customer scope. Label the scope, provide explicit Alla konflikter, and never silently apply narrower filters beneath a broader count. Normalize whole logical groups, fetching complete associations/participants even when a peer booking falls outside the displayed scope. A queue row represents one logical conflict, not one persistence association. Multi-person conflicts can appear in relevant person/date groups but the chip counts distinct logical identities. Date grouping uses Stockholm conflict-window start date with the full interval visible; spans are not truncated.

A checked manager snapshot returns complete current detector facts plus workflow/booking/series baselines and an SQL snapshot timestamp. Server runs the sole pure detector over those facts for the queue/count and joins current accepted state only by exact identity. This is a read/scan, not an unaudited workflow mutation. New derived groups lacking persisted rows can be displayed with natural identity; finalization validates/materializes them atomically before any decision. Use the same scan projection for manager counts and resolver queue under identical scope. Never expose raw detector facts to browsers or own-only roles. Last checked denotes this actual successful scan's fact snapshot, not an ordinary SELECT time or a claim that no later writes occurred. A failed/partial scan exposes unknown plus retry, not a zero count or Inga konflikter. Latest-request ordering rejects out-of-order responses.

Detail presents both colliding bookings and their individual intervals, or the complete multi-booking capacity/breach window; include only authorized context labels, no money. If multiple participants can move, require explicit booking selection. A focused text timeline is an accessible minimum, with the visual timeline supplementing it. Reuse BookingConflictPanel's labels/styles and existing editor; a temporal endpoint-only arrow without the participating bookings is insufficient.

## Actions and bounded convenience

Flytta opens the existing time/editor flow for the explicitly chosen booking. The default finite search is the next fourteen Stockholm local dates starting on the selected booking's local date, with fifteen-minute local start candidates plus exact shift/access-window/booking-end boundaries, and the earliest ten distinct zero-candidate-conflict results. Deduplicate canonical intervals and sort by start/end. Preserve elapsed duration for timed bookings and local-day span for all-day bookings; apply existing gap/fold policies and reject nonpositive windows. The bound/step/result cap live in one tested constant used by server/UI. Users can choose other times manually; no exhaustive availability/optimization claim is made. A candidate is available only when the shared detector has no groups involving it across all assignees and current job inputs. Unrelated existing tenant warnings do not disqualify a suggestion. Unknown facts, cancellation or failed evaluation never mean free.

Omfördela starts with the active matching-work-role roster and evaluates the proposed replacement set through the same detector. Preserve other assignees unless explicitly changed; show actual weekly-schedule capacity/load, not employment percentage or generic weekday assumptions. No implicit crew-wide replacement, overtime authorization or new resource/competence rules.

Justera reuses existing single-occurrence shortening/time/assignee/connection edits and scope controls. UX's split affordance is the existing reviewed Detta och kommande series split; no new arbitrary standalone one-to-many booking split is defined. Warned edits still use current full warning acknowledgment/nonblank reason; only complete selected groups become accepted. A targeted conflict remaining after adjustment stays open/accepted and the result explicitly says it remains; mutation success is not resolution success.

Acceptera konflikt changes workflow, with required nonblank bounded reason and current complete target selection. It does not change booking times/assignments or make an occurrence an exception. No blanket accept by row/page/person/date/series. Default queue excludes accepted, while Visa accepterade retains inspectability. Acceptance and adjustment both write one immutable action/outcome record; notify the affected assignees as the approved UX requires, using truthful action-specific wording.

## Immutable outcome/history and complete refresh

Use one new append-only `booking_conflict_resolutions` table as supporting infrastructure for required durable history and idempotent resolver outcomes. A row binds tenant, current actor, command UUID, canonical request digest, action/outcome, canonical target keys, a same-tenant anchor booking, validated affected-booking IDs, SQL timestamp, audit/event identity and safe durable result. Unique tenant/actor/command identity rejects changed-content reuse. A same-tenant composite FK protects the anchor; checked finalization validates every affected ID. No authenticated direct INSERT/UPDATE/DELETE, no mutable outcome-only write on bookings. FORCE RLS and explicit manager-only minimal read columns/checked wrappers; anonymous/cross-tenant/own-only callers cannot inspect it. Existing append-only audit still commits once, without a new raw audit SELECT grant. A narrow history projection exposes action/outcome/actor label/time and permitted context; do not ship private request/result/proof fields.

Rationale: current conflict anchors can later disappear even after successful acceptance or an adjustment with remaining warnings; storing the replay result on that row is fragile unless every subsequent deletion/state transition becomes ledger-aware. Storing accept-only results on bookings would invoke the unconditional occurrence-exception trigger or need a privileged special-case bypass. One immutable command/history ledger separates those concerns and serves both required replay and Händelser. This adds no product surface outside approved resolution/history and is explicitly manifest/H4 enrolled. It is a proposed technical decision pending Root's independent specification validation.

All three effective complete-set writers must use a shared private refresh helper introduced by a forward migration: booking_commit_editor_internal, finalize_booking_series and finalize_job_card. Preserve matching open/accepted records and accepted actor/reason/time; insert new identities open; remove absent non-resolved derived rows; retain absent resolved rows. If a resolved key becomes current again, reopen it and clear terminal workflow metadata as constraints require; immutable ledger/history is untouched. Exclude historical resolved associations from active aggregate normalization. Resolver finalization identifies the complete pre-edit target groups and only marks disappeared targeted groups resolved with the action/actor/SQL time. Preserve/materialize those exact targeted association rows as resolved before a complete-set refresh can remove absent non-resolved rows; a newly detected snapshot target without persisted rows is materialized from the validated snapshot/output rather than fabricated client data. This ordering retains the promised resolved workflow rows, while the independent immutable ledger keeps replay/history durable regardless of later workflow state. Current surviving/new groups follow normal selective acceptance; no unrelated status change. No physical history deletion or rewrites of old migrations.
