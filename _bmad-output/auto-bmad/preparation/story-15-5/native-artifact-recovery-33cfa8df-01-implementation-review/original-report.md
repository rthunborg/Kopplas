## F1 P2: Reader termination is reported as physical EOF and verified custody

Location: Root driver `Lines.reader` lines35-40, `Lines.line` line49 / `Lines.discard` line57, and final custody decision lines145-148. Caller: the authorized Root driver's actual main loop and failure cleanup for its owned helper stdout.

The reader always queues `None` in its finally block, including after a read exception, queue failure or output-cap break. Consumers interpret that same sentinel as `self.eof=True`. Final custody then requires child exit, this eof flag, reader join and a settled last transport (or logical_attempts==0), but does not exclude `lines.bad`. Thus a reader failure before observing any actual end-of-stream can be persisted as reader_eof=true and `OWN_HELPER_GH_HANDLES_AND_OUTPUT_SETTLED`. No downstream validator corrects the final Root result. The zero-observed-stage branch also cannot turn lost transport messages into proof that none occurred.

Independent reproduction exercised the actual driver main with memory-only Root storage, a bounded synthetic Python stdout child and a reader whose first read raises OSError. The control did not expose the synthetic error text. Driver exit was 1/outcome STOP_NO_RETRY/category CAP_EXCEEDED, but the final captured state falsely had reader_eof=true, reader_joined=true and the verified-custody string above, with stdout_bytes 0/logical_attempts 0. The failing reader had never returned EOF; queued child output was not read by it. This is a concrete failure-truth/custody defect even though the operation remains failed.

Required correction: distinguish actual empty read/physical EOF from reader-thread completion, I/O failure, queue overflow and cap overflow using closed flags/categories. Preserve those facts durably. A completion sentinel must not itself establish EOF. If bounded cleanup cannot establish actual output EOF and required tracked transport settlement after reader failure/lost messages, preserve CUSTODY_UNKNOWN regardless of helper exit or zero observed logical stages. Add actual driver-main synthetic controls for reader exception and overflow, checking false/unknown EOF and custody, no terminal mutation or continuation, no raw error persistence and no retry. Keep existing queued-after-exit success behavior.

## F2 P2: Partial transport output becomes a false zero byte count

Location: helper `bounded_command` lines264-289, particularly initializing info.stdout_bytes=0 at line266 and updating it only after pipe_read returns at line271. Caller: recovery main's fixed listing/ZIP getter and its bounded transport refusal path.

`pipe_read` accumulates bytes locally, then raises on timeout or cap. That observed progress is discarded by the exception. Cleanup may drain further output, but its bytes are also discarded from the transport facts. The stage subsequently reports stdout_bytes=0 despite having consumed a response. This does not satisfy the plan's requirement for accurate bounded byte/digest evidence; zero is an asserted measurement, not an unavailable value.

Independent real, bounded offline subprocess controls reproduced both paths. A 200-byte synthetic stdout with cap 20 raised CAP_EXCEEDED and reported spawned=true/settled=true/stdout_eof=true/stdout_bytes 0, even though the cap refusal itself requires at least 21 bytes observed. A separately instrumented partial-output timeout confirmed seven bytes actually returned through os.read while the reported counter remained 0. The latter child was killed/waited within the bounded control. None of these processes was gh or the collector, and no HTTP request occurred.

Required correction: carry bounded observed byte count and digest state through exceptional reads and cleanup, distinguishing any captured/drained/discarded progress or explicitly unknown completeness. Never replace observed progress with zero. Keep raw bytes memory-only. Ensure the closed transport schema can represent the bounded cap+1 overflow observation honestly rather than clamp/reject its own failure proof. Add counter/digest assertions to cap and partial-output timeout controls, including final Root failure handoff, and preserve one-shot/no-retry behavior.
