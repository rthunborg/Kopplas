## F1 (P2): table-level SELECT is not a necessary status privilege

Location: plan.md:36 and :61 (fixed `owner_tokens_select` predicate and the one-false-required-bit decision).

The proposed eighteenth bit is `has_table_privilege('calendar_feed_owner','public.calendar_feed_tokens','SELECT')`. The bound status function at migration:153–155 performs SELECT * on that relation, but PostgreSQL permits those reads through SELECT grants on all referenced columns even without table-level SELECT. PostgreSQL 17.6 `ExecCheckOneRelPerms` first checks relation privileges and then checks missing SELECT privileges at column level, including all columns for a whole-row reference. Thus this bit measures a table ACL; false does not prove an effective SELECT gap.

Caller and consequence: Root interpreting the future qualified controlled status observation can encounter ACL_ENGINE with this as the only false measured bit while all token columns are selectable. An unmeasured dependency (for example the status function's JSON-building built-in) can still supply the ACL error. The plan explicitly does not measure all built-ins. Applying the decision row as if all eighteen bits were necessary would create a misleading missing-necessary-privilege candidate. The existing identity, function-source and cleanup checks do not establish equivalence between table-level and effective column permission. This is a reachable PostgreSQL permission configuration, not an assertion about the historical run or a claim that such grants currently exist.

Smallest correction: retain the eighteen booleans but explicitly mark `owner_tokens_select` as table-ACL-only, exclude its false value from necessary-privilege conclusions, and route the lone-false-token case to STATUS_ORIGIN_UNRESOLVED. Alternatively a separately specified, reviewed fixed predicate may establish full required column coverage within the same SELECT; no new query, grant or privilege elevation is justified. Add a decision/control case for table SELECT false with effective column coverage true. No functional source fix is requested by this finding.

Primary support retrieved 2026-10-21: [PG17 privilege inquiries](https://www.postgresql.org/docs/17/functions-info.html#FUNCTIONS-INFO-ACCESS-TABLE) distinguish table and column inquiries; [PG17.6 executor source](https://raw.githubusercontent.com/postgres/postgres/REL_17_6/src/backend/executor/execMain.c), lines 623–674, explicitly permits column-level satisfaction. Its short explanation is: “some of the bits can be satisfied from column-level rather than relation-level permissions.”
