# Story 15.5 current contracts and design

Author: gpt-6.1-sol High, 2026-10-20. Candidate planning decisions under the owner's October15 design-default authorization; no legacy observations. Source baseline `159557e114f18123e73282c39c90830917de9948`. These decisions need Root's distinct High validation before implementation.

## Capability and current subject

The capability is one tenant-membership's own scheduling feed, never a manager's team scope. Derive tenant/user/membership from the authenticated context for management and from the hashed token row for fetch. Recheck active tenant, active current membership and current Bookings.View permission at each operation, under compatible locks; map membership through person_profiles.membership_id to booking_assignees. No profile yields a valid empty calendar; it never broadens to tenant bookings. A shared booking appears once without co-assignee IDs/names. Reassignment/removal, cancellation and membership/permission loss remove eligibility on the next committed fetch. Rejoining must not reactivate an old revoked capability. Tokens bind immutable membership IDs, not email.

Do not call readScheduling for public reads. Its client is cookie-bound; managerial personal data can include team rows for presentation filtering, and it brings conflicts/capacity/options. New SQL projection joins only exact current subject assignments and permitted labels; no full jobs/customer/contact rows enter application memory. E16 lead/member scope does not imply feed assignment. The feed is read-only and never invokes booking proof, preview/finalize, capacity or mutation protocols.

## Issuance and race semantics

Node crypto.randomBytes(32).toString('base64url') produces a canonical 43-character capability; SHA-256 of its canonical UTF-8 representation is the lookup key. Store no plaintext, encrypted escrow or recoverable URL. One active token per tenant/membership; table also records created_at/revoked_at/last_used_at/usage_count and lifecycle revision/attempt metadata. Manage functions are checked authenticated narrow RPCs with ordinary JWT and SQL-owned audit in the same transaction, explicit actor/current authority checks, exact function grants and no direct DML. Raw token is returned only in the successful issued URL; no audit, errors, logs, browser storage, analytics or traces may contain it.

Create/rotate are expected-revision/attempt-bound. Rotation atomically revokes old and installs new; failed audit/write leaves old usable and no new active token. Concurrent operations serialize on subject/lifecycle state. Exact already-applied retry returns sanitized committed metadata, never reconstructs a raw URL or rotates again. An uncertain issued response is reconciled by status/attempt read; show that the link could not be recovered and offer a separate explicit rotation, rather than automatically generating another capability. Revoke is idempotent and audited once per actual transition. UI retains pending intent and exposes retry/reconcile; no success before confirmed persistence. PostgreSQL commit order defines concurrent fetch/revoke: a fetch whose authority snapshot was admitted before revocation may finish, but a subsequent fetch cannot succeed. Do not promise recall of bytes already downloaded by external calendar software.

## Narrow anonymous database boundary

The public handler uses a new cookie-less anon-key client, no service-role client and no auth/session resolution. A dedicated least-privilege NOLOGIN NOINHERIT owner runs only checked feed functions with empty search_path, exact table/column grants and narrowly filtered Vault-key access; no caller can assume this owner. The sole public fetch RPC accepts a server-signed request over schema/domain, token hash, canonical IP hash, issued/expiry instants and request UUID. A separate domain signs authenticated lifecycle inputs (actor, tenant, membership, action, expected revision, attempt and new hash). Both use a dedicated feed-only 32-byte-or-stronger key, not a JWT/service-role/E12/booking/quote key. Length-prefix UTF-8 fields and verify the same payload in Node and PostgreSQL; max attestation lifetime60seconds, reject future/stale/mismatched inputs. Secrets/proofs never cross the browser or audit boundary. This prevents direct anonymous RPC callers choosing a fresh IP hash and authenticated callers inserting weak chosen token hashes. Valid proof still authorizes only the presented capability's minimal read and bookkeeping, never arbitrary tenant/subject input or privileged commands.

This is supporting infrastructure for independent per-IP enforcement, not a fourth public surface. Isolated tests inject a fresh test-only key into the owned runtime and Vault with redacted receipts. Hosted key provisioning belongs to release operations before explicitly authorized hosted feed enablement; no secret is claimed present and this plan authorizes no env/provider/hosted mutation. Missing key fails closed with a generic unavailable response; it must not fall back to unsigned RPC or service role.

## Independent limits and monitoring

Default fixed UTC windows:900seconds,60 successful-capability attempts per active token and120 requests per canonical IP hash across tokens. Constants live in one server policy mirrored/validated by SQL; tests inject clock, not caller-selected limits. All request shapes including unknown/revoked/rotated/malformed consume the same IP axis; active tokens additionally consume token axis. Each axis is independently atomic under concurrency. Malformed input maps to an inert hash sentinel internally. Invalid token classes return identical404 generic text/content type/security/cache headers and no Set-Cookie, Location, IDs or differing tenant messages, unless the common IP limit yields429. Do not use a revoked-only token-limit response that distinguishes it from unknown.429 carries Retry-After to the fixed window boundary. Database/network/proof failures return uniform503 with no partial calendar; never represent failure as an empty calendar. No ETag/304/cache shortcut bypasses current revocation checks.

Keep per-token counters/spike flags on the tenant token row. Store cross-token IP windows in `calendar_feed_ip_windows`, a global infrastructure table with no tenant or subject FK, no raw IP, no token association and no exposed DML/SELECT. Roll expired windows forward/prune only bounded expired counter rows within the checked request transaction; this is counter housekeeping, not a product retention program. Keep cardinality/work bounded under distinct-token/random-input attack; failed/limited requests still persist sanitized counters rather than exception-rolling them back. Safe Admin-only queue on the management page shows tenant aggregate counts and spike timestamps, not hashes, raw IP, raw URLs or peer booking/person details. Ordinary users see only their own token status/last fetch/usage. This fulfills ADR-B004 monitoring without a new notification category or runner.

Trust only a deployment-verified Vercel platform IP header in its recognized platform context; canonicalize one IPv4/IPv6 address, never the first element of arbitrary user X-Forwarded-For. Missing/ambiguous/untrusted IP uses one shared conservative unknown-IP bucket, not user-controlled identifiers. Local route tests use that same fallback; lower-level deterministic tests inject trusted IP through a server dependency seam unavailable to HTTP input. Hosted network/proxy trust must be verified by release operations before enablement; current topology is not inferred. HMAC the canonical IP with a dedicated domain before SQL; no raw IP persists.

## Calendar serialization and usable settings

Feed route `/calendar/feed/[token]` under `(public)` produces UTF-8 text/calendar via ReadableStream only after a complete authorized database result; no stored feed, ISR or shared caching. Feed all currently materialized own planned bookings, collected completely using JSON/bounded internal paging rather than silently dropping rows at PostgREST1000. No arbitrary server date horizon or truncation is introduced. Stable booking UUID-derived UID has a fixed non-tenant suffix and survives edits/series split where ID survives. No RRULE expansion: E15.2 materialized exceptions are authority; cancelled tombstones are omitted, cancellation/removal is reflected by omission from the next full subscription. UTC Z timestamps preserve actual timed instants. All-day events use Stockholm local DATE DTSTART/exclusive DTEND from actual boundaries; test both DST transitions. DTSTAMP/last-modified use stable current booking update time. No attendees/organizer/URLs/alarms/notes/conflict reasons/contact emails/phone/tenant or assignee IDs. SUMMARY uses a safe work-role label or `Bokning`; allowed job/customer labels and facility address become minimal summary/location. A free-text booking description is not a safe title because it may contain other people's details. Serialize RFC5545 CRLF, escaped text, newline injection resistance and75-octet UTF-8-safe folding. Independent parser/known byte fixtures cover these properties.

Add a profile-menu `Min kalender` link to protected `/settings/calendar`, with title `Kalenderprenumeration`. Existing personal scheduling agenda is linked from there; no new primary sidebar module. Own management and optional Admin abuse panel have separate server DTOs. Show plain-language Swedish warning that anyone with the link can read these bookings and a calendar provider may retain previously fetched events; show fresh URL/copy control only after create/rotate, status, `Senast hämtad` (never-used explicit), rotate/revoke confirmations, pending/error/retry/reconcile states. In-memory issued URL only; revisits explain rotation if the link is lost. Clipboard denial has a selectable accessible input fallback. Maintain existing tokens/styles/Dialog, labels, focus return, keyboard and 360×640 touch usability. Headless types/validation/actions/state and iCalendar encoder remain independent of settings presentation.
