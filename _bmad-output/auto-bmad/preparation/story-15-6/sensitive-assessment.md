## Exact proposed read contract

`src/features/my-day/types.ts` owns browser-safe types. `src/server/read-models/my-day.ts` owns current tenant resolution, existing capability checks, typed RPC parsing, a failure union and strict DTO construction. It must use the ordinary cookie-bound client; injected clients are test seams only. No client actor/tenant/person selector.

The RPC must independently require auth.uid(), active membership in p_tenant_id, existing admin/project-leader/Montör authorization, finite non-null start/end, end>start and a maximum eight-day interval. Every join matches tenant_id. Derive the actor from auth.uid(), never a supplied actor/person ID. Use stable read-only SQL, security definer with empty search_path only because the projection must safely read restricted CRM labels; revoke PUBLIC/anon/service_role execution and grant only authenticated. This is a checked projection, not a new tenant-wide table grant.

Return one JSON object with arrays `ownSelfPersonIds`, `bookings`, `activeJobs`. Use one database snapshot for these linked facts; do not publish partial pages as a complete week.

- ownSelfPersonIds: IDs of unarchived person_profiles joined to active tenant membership belonging to auth.uid(). Never include another person's ID.
- bookings: planned rows overlapping [start,end), with EXISTS booking_assignees→own profile→current active membership. Apply this predicate even for managers; management entitlement never broadens Min Dag. Sort startsAt,id. Exact row fields: `id, startsAt, endsAt, allDay, description, workRoleLabel, jobId, jobLabel, customerLabel, location`. `location` is null or `{street,postalCode,city,countryCode}`. Add no assignee array, crew names, contact details, price fields, audit IDs, command outcomes, conflict reasons, roster or options. For reporting reuse, own IDs can stay server-side unless the existing TimeReportActionDescriptor consumer requires them.
- customerLabel: booking.customer_id first, otherwise linked job.customer_id, using current tenant-matched customer.display_name. Do not emit a CRM link for Montör.
- workRoleLabel: tenant-matched work_roles.display_name or a neutral Bokning fallback; jobLabel is jobs.title, with a neutral Jobb fallback when null. Keep booking description separate so job/customer identity never depends on parsing free text.
- location proposed owner-authorized design default: explicit booking facility address wins; otherwise job location override; otherwise job facility address; otherwise null. For a standalone booking only its explicit facility contributes. This preserves the booking's explicit place while respecting E16 job override for the inherited location. Do not substitute customer billing address or fabricate coordinates. Record this choice in story design decisions because existing feed omits the job override, while E16 job detail includes it.
- activeJobs: same explicit tenant and current relationship semantics as personal `read_job_cards`, additionally `archived_at is null` and status in `created,in_progress`. Exact row fields: `id,type,title,status,customerLabel,plannedStartDate,plannedEndDate,myRole`. Also require job_can_read; do not conflate job readability with personal relationship. `myRole` is `arbetsledare` for an unarchived own job_member designation, `member` for other current own membership, `booking_assignee` when the relationship is booking-only. Resolve precedence in that order. Do not return another member or create a new role. UI labels can be Arbetsledare / Medlem / Bokad. Existing relationship semantics deliberately include historical/cancelled booking assignments; do not silently redefine that helper in this story.

## Focused High amendment — pending-jobs isolation and landing

2026-10-25; explicit parent follow-up; gpt-6.1-sol / High. This amendment supersedes the proposed three-argument RPC signature and resolves the earlier routine landing default. No implementation or executed verification is claimed.

Approve the four-argument shape with the following mandatory conditions:

`public.read_my_day(p_tenant_id uuid,p_start timestamptz,p_end timestamptz,p_include_jobs boolean default false) returns jsonb`.

`src/server/read-models/my-day.ts` derives p_include_jobs exclusively from the server-imported `SCOPE_MANIFEST.modules` jobs status being exactly `active`. No page/action/query parameter, cookie or client DTO can supply or override it. Missing/unknown/pending status maps to false. The function treats null as false or rejects it; it must not accidentally enter the true branch through a nullable condition.

The false branch must execute a separate SQL projection with no reference to public.jobs, job_members, job dependencies, read_job_cards, job_can_read, job_has_current_relationship or another helper that reads job data. An optional JOIN guarded by a boolean is not sufficient evidence for the zero-job-query contract. Return activeJobs=[]; booking jobId/jobLabel are null (or absent in a separately validated closed DTO), and derive booking customerLabel/location from the booking's explicit customer/facility only. There is no fallback through job foreign keys or job-derived customer/facility/location, no own job-role calculation and no job action. Server DTO construction also suppresses job fields/actions when jobs is pending. A raw booking job foreign key must not become a hidden job surface.

The true branch may enrich or return a job only after both current job_can_read(tenant,id) AND job_has_current_relationship(tenant,id) hold, with tenant equality on every join. Apply those gates to booking-linked job label/location/customer fallbacks as well as the activeJobs list, even though a live own booking normally establishes the relationship. ActiveJobs retains its nonarchived created/in_progress restriction. A true boolean is merely a server composition choice and never a grant: it cannot replace current actor, membership, capability or per-job relationship checks. Direct authenticated RPC callers can supply true; they still receive only already-authorized personal job projections. The argument alone is not a database-enforced proof of manifest state. If the requirement is to prohibit direct authenticated RPC job reads while the deployed manifest says pending, a client-supplied boolean cannot enforce that stronger boundary: require a trusted database activation source or an inaccessible internal job projection. Do not claim that stronger protection from this flag.

Booking-only time reporting in the false branch must not reintroduce job data through prefill or call an eager job-option reader. Check the existing filing contract before presenting an own booking with a stored job link but a withheld jobId: if that contract requires the matching job ID, withhold that booking's report action and offer the existing safe time-report route only if it respects the same pending-module composition boundary. Do not weaken filing integrity or invent a null relationship to satisfy presentation. A minimal internal boolean such as canReportBooking may control this omission without disclosing the job ID. Any proposed broader module-pending time-report rewrite is outside this preparation change.

Required focused evidence: with jobs pending/false, a query spy proves no job table/RPC/helper is called, no job foreign keys/labels/location fallbacks/roles/actions occur, and bookings with explicit customer/facility still render correctly; with jobs active/true, unauthorized/foreign job joins cannot contribute labels, address or role, and only current authorized personal active jobs appear.
