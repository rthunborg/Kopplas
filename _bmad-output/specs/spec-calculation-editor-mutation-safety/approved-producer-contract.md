## Atomic expected-state contract

Choose **expected content**, not a new aggregate revision system. Use the original server-projected facts already supplied to the form; do not recapture them immediately before dispatch. Define a closed version-1 canonical JSON shape per operation in the feature-local helper and SQL validator; reject missing/extra keys, normalize optional/null and numeric serialization consistently. The SQL compares the supplied expected facts to current persisted facts under locks in the same transaction as the write. The authoritative SQL/RPC validates and normalizes the actual typed input and computes the canonical request digest itself from its resolved actor/tenant, operation kind, target/parent, complete normalized intended input and expected facts. It never accepts an arbitrary action/client-supplied digest as payload binding; direct authenticated RPC calls receive the same normalization, checks and digest computation. Hashes are identifiers, never authorization or new valuation arithmetic.

- Header title/status edits compare original values of every submitted field plus current lifecycle context; tax update compares the complete original tax snapshot and lifecycle context. A concurrent disjoint field edit may coexist; an obsolete value in the actual write set returns `COMMAND_CONFLICT` without a domain write or audit. Same-valued current state does not prove an earlier operation committed.
- Section and row edits compare their complete original projected target fields, including row source snapshot/type/VAT/option/inclusion facts and parent/lifecycle context. Reuse existing validators, source-resolution and invariant rules. SQL must recheck the effective persisted/source facts used to derive a patch inside the transaction; a TypeScript read before the lock is insufficient. This adds no financial arithmetic or rounding rule.
- Row archive compares the full original row. Section archive compares its original section plus all active child rows, membership and order. Calculation archive compares its header and complete active section/row subtree. These are **soft archives**: existing header/section/row archive effects are unchanged, without cascading child archive flags or hard deletes. Comparing descendants prevents hiding a newer child edit/addition under an old parent decision. Files/links keep their existing independent lifecycle and locks.
- Each reorder compares the entire original active sibling ID/order set and requires the desired IDs to be a duplicate-free complete permutation of that same set. Concurrent insert/archive/reorder causes conflict; no partial rank update or omitted sibling overwrite. Concurrent edits to an unrelated label remain intact because reorder writes only ranks. Both existing reorder commands remain atomic.

Serialize editor mutations for an existing calculation by locking its root header before affected sections/rows in ID order; creates recheck parents and row limits under that lock. Revoking ordinary authenticated direct writes and old unchecked RPC execution is part of this same cutover, so another admitted application path cannot skip those locks/predicates. Preserve the existing tenant/actor gate and source locks. Use the current tenant-operation lock order where shared role/source records are involved, then operation, calculation and descendant locks consistently; bounded lock/statement timeout is an uncertain result, never proof of rollback. New concurrency tests must exercise both lock order and existing producer/source interactions.

## Durable operation/result contract — one scoped table

Create **`public.calculation_editor_operations`**, enrolled solely in the already-active `calculations` manifest module. This is necessary even for known-ID writes: later writes, archive or privileged target removal can erase the evidence needed to distinguish an original commit from coincidentally equal current values. One closed proof table is smaller and more reliable than adding per-target birth/history columns, a new aggregate revision system, or reusing the unrelated settings/pricing operation store. Existing quote authorization linkage is used for its real authority purpose, not widened into a cross-feature ledger.

Store only: globally unique operation UUID; tenant and original actor; closed existing command kind plus calculation form discriminator; target/parent/calculation IDs as applicable; protocol/request digest; `prepared | committed | closed` status; quote-only bound authorization ID and original capture timestamp; immutable terminal code or committed target/quote/version-number/count identifiers and commit timestamp. Do not persist submitted text, tax answers, money amounts, raw expected facts or attachments. No target/actor FK that deletes historical proof; the tenant FK follows existing tenant-owned lifecycle. No expiry, cleanup API or new retention program. A quote prepared authorization still expires under ADR-B008; that does not delete the operation or revive authority. Add tenant/actor lookup indexing and a unique bound authorization constraint. Terminal proof is immutable; only the checked SQL path can transition a prepared record once.

Every first valid mutation takes an operation-key transaction lock and reserves that identity. Domain change, required audit/event, final result and terminal proof commit together. Unexpected failures roll the transaction back. The same identity/digest returns the original proof without another write/audit; another payload/kind/actor/tenant cannot reuse it. Current authorization is checked **before lookup/replay**, with current target/parent access checked before exposing result IDs. A removed or no-longer-readable target yields an authorized historical-commit indication with unavailable target, not a resurrected record or hidden data. Known definitive conflict may be committed as a closed no-domain-write outcome; a corrected request requires a new intent after explicit user refresh/decision.

An absent lookup can mean an uncommitted/in-flight request, so it returns **unconfirmed**, never “not executed.” Explicit replay with the original identity and original input serializes behind any first attempt: it either obtains its result or safely executes once after a proven rollback. The identity is not a bearer capability. No automatic replay, background queue or new intent is permitted while the old result is uncertain.

### Initial quote creation preserves ADR-B008

Keep the existing seller versus admin/PM source projections, mandatory reviewed digest/date, current source checks, 15-minute one-time authority, atomic authority consumption and quote/event/audit creation. Add three narrow wrappers around these existing semantics:

1. `authorize_calculation_editor_quote` checks current authority and request identity before building a new binding. For a fresh intent only, it invokes the existing role-appropriate initial-review authorizer and atomically stores **that authorization and original capture time** in a prepared operation. Its digest binds the reviewed digest/date and selected attachment IDs. Repetition reuses that exact authorization; it never issues a fresh one for an existing intent.
2. `create_calculation_editor_quote` locks the operation and its bound authorization, rereads their actual state after acquiring those locks, and uses only that authorization/original capture/correlation. It invokes the existing initial-create/consume logic and stores the returned quote/version/number proof atomically. A prepared retry enters this SQL path directly, without rebuilding/replacing the reviewed snapshot. Preserve existing source/actor checks and add a real current-expiry check after all relevant lock waits, immediately before consumption/insertion, using current wall time such as `clock_timestamp()`, not transaction-start `now()` or a pre-wait `statement_timestamp()`. The existing private consumer's statement-time guard alone does not establish this proposed post-lock rule. A waiting creator must reread a committed terminal closure and refuse to consume that closed intent. Definitive stale/expired authority becomes noncommit only when a checked transition under the operation lock commits a closed outcome; new creation then requires a new explicit review and new intent. A subtransaction must roll back any failed domain work before committing that closure. Read-only reconciliation never closes an operation: a merely prepared record remains unconfirmed even if the observer's clock says its authorization has expired.
3. A committed replay returns historical result proof after current authorization/access checks, even if its once-consumed authorization has since expired. This creates nothing, grants no authority over new content and never changes its existing PDF/source fingerprint. Prepared or expired **unconsumed** authority is never treated this way.

The other public interfaces are `mutate_calculation_editor` (closed eleven calculation kinds) and read-only `reconcile_calculation_editor_operation`. Together these are four new public RPCs, not a generic mutation dispatcher. Existing initial authorizers/create-consumer and calculation header/reorder functions become private implementation helpers, with old authenticated execute grants revoked; successor/final-send authorities remain unchanged. Authenticated direct INSERT/UPDATE/DELETE on the three calculation tables is revoked, retaining authorized SELECT; the new checked wrappers are the only application mutation routes. Existing immutable/source/row-limit constraints and no-delete policy remain.
