# Story 35.1: Authority And Base Contract

## Status

Documentation/readiness preparation only; not approved or ready-for-dev. No implementation admission, code allocation or tracking transition. This 2026-10-26 applicability correction replaces the live-UI template obligations formerly attached to AC4–AC7; IDs remain stable and refer to the documentation checks below.

## Story

As the planning/test-design reviewer, I want a source-pinned authority, dependency and applicability handoff, so that each slice receives appropriate test design without unrelated runtime requirements.

## Intent and scope

IN: documentation, authority-crosswalk consistency, dated base evidence, source/spec hashes, route inventory, per-slice applicability and scoped handoff. Retain incorporated detailed requirements and historical evidence. No UI, server action, schema, upload or application test is delivered by 35.1. Actual implementation requirements remain with E35.2–35.19 and applicable E17/E18 owners.

## Acceptance Criteria

1. **E35-1-AC1 — Authority coverage.** Account for 17 MAIN rows, eight FIELD rows, five frozen Phase A journeys and B1–B7 through authority/screen-state crosswalk and actual route allocation. Each has an owner/destination or explicit retained, future or excluded disposition. Preserve detailed rules/deep links; no retirement without atomic destination/incoming-link proof.

2. **E35-1-AC2 — Dated base evidence.** Distinguish authoring checkout, integrated inventory and dated remote observations. Record revision/date/provenance/hashes and missing evidence. Do not relabel the 2026-10-23 snapshot as current on 2026-10-26. Unverified ancestry/ownership/DT-B15 remains a later admission dependency; historical reservations allocate no paths.

3. **E35-1-AC3 — Scoped handoff.** Classify slices as documentation checks, concrete test design now, material-decision-blocked contracts or dependency-bound migrations. E17/E18 gaps do not block unrelated E35 design. Name inputs, outputs, boundaries and next owners without approving or starting implementation.

4. **E35-1-AC4 — Link/hash/index consistency.** Validate new relative file links, output hashes and index/spec identities. Recompute changed output hashes while preserving historical input hashes. Record source drift rather than concealing it. Hash identity is not readiness or product correctness.

5. **E35-1-AC5 — Applicability.** Every generated spec distinguishes requirements applying to its own changes, inherited regression obligations and N/A with scope reasons. Add no dialog, form, file operation, command, viewport or application suite merely to satisfy a template.

6. **E35-1-AC6 — Preservation and ownership.** Compare all eight original E17/E18 sketch/EP-06 sections verbatim; retain their unresolved blockers. Keep completed evidence and linked follow-ups intact. Record code conflicts without claiming/releasing paths or changing E15/tracking.

7. **E35-1-AC7 — Honest evidence.** Publish documentation-check results/limitations separately from downstream runtime/release evidence. Preserve actual owner requirements for money/provenance/projections/transactions and release checks; no source mapping is a runtime/test-design PASS, release approval or implementation admission.
