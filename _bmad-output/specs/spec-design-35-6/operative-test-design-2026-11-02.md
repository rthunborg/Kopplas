## Authority and fixture contract

`readCustomerList` selects exactly id/type/display_name/org_nr/email/phone/city/archive/create columns: personnummer never enters the list payload or search. `readCustomerDetail` intentionally returns personnummer to the entitled detail client; default masking/reveal is presentation, not a security barrier. Do not strengthen the test into 'no detail PII payload' or move PII into URL/log/session storage. `CustomerListRow`, `CustomerDetailRow`, `FacilityRow`, `ContactRow` and `CrmActionState` are existing read-only DTO authority; UI must not synthesize entitlement or freshness fields.

Nine actions dispatch through runCrm → runCommand → current checked RPCs on request-bound RLS clients. Tenant/actor derive server-side. Input validation, parent existence/ownership, role checks, transaction/audit atomicity and same-tenant FKs remain authoritative; neither a hidden customer_id nor returned DTO grants permission. A contact's optional facility follows existing checked same-tenant parent rules; do not introduce a same-customer policy not already enforced. `is_primary` is a convenience flag, not uniqueness authority.

Customer update alone carries complete `expected_customer` comparison facts. `20261029132339_customer_update_expected_facts.sql` locks the tenant/customer row, validates all original facts including nullable values/archive instant/type, rejects stale facts with PT409, patches within type and records its bound audit in the same transaction. The old five-argument overload fails closed. Existing integration tests prove equal-baseline concurrent winner/conflict, all fact comparisons, actor/tenant/role denial and audit rollback. Facility/contact update inputs have no expected-facts contract. ArchiveInput is exactly `{id}`: no archive reason.

Customer safety storage is one payload-free unresolved hint, not a receipt/replay key/draft. Only the owning live attempt clears a definite result. Lost response, SERVER_ERROR, mismatching targetId or unavailable/corrupt storage blocks further customer dispatch, including reopen/remount; current code has no unknown-outcome reconciliation API. Read refresh for a known COMMAND_CONFLICT is a different, consented discard-and-review path. Do not equate it with unknown recovery.

Fixture seams: existing CRM E2E reads the established local `.auth/fixture.json` (company/private customer A, facility, tenant-admin credentials); use values without printing credentials. Its `customerSnapshot`, `openCustomerCreate`, `openCustomerEditor`, `customerActionGate` and `createTwoTenantFixture` already supply actual command, lost/held response, two-editor, empty/foreign/revocation observations. `tests/factories/tenants/crm.ts` supplies customer/facility/contact seeds; `tests/factories/tenants/index` exposes the two-tenant family. Integration CRM suites use request clients plus independent administrative observation. For additional UI lifecycle rows, use a unique per-test customer/facility/contact marker and existing fixture factory imports; do not rename/archive the common company/private seed or mutate the shared auth fixture. Only test-owned records/memberships may be changed and restored/cleaned through existing test helpers.
