## Contract: capture before dispatch, then keep the attempt immutable

Before the first mutation dispatch, capture in the owning mounted form: operationId UUID; operation kind; form generation; target identity (row ID for existing rows; singleton kind plus expected absence for an empty singleton; proposed target UUID for every first create); expected write_revision or explicit absent marker; exact validated request candidate; and the actor/tenant UI context associated with that attempt. Allocate the identity synchronously before calling the action, not in its response. The server resolves actor/tenant afresh; submitted context is never authority. Bind initial envelope correlationId to the validated operationId, as existing job actions do. The committed audit correlation remains that original ID through replay.

The server/SQL request fingerprint includes protocol version, resolved tenant and actor, operation kind, captured target/proposed ID, expected row ID/revision or absence, and the complete canonical validated mutation payload. Preserve null versus omitted semantics: in particular company logo_url_present is part of the digest; omission preserves the stored logo, and explicit clear remains distinct if supported by the existing command path. Preserve current trimming, optional fields, integer öre, bp and optional blank WorkRole cost=0. Raw browser values or client-supplied hashes do not establish the server fingerprint. Approval timestamps are generated once at commit and stored in the receipt, never freshly fingerprinted on retry.

Retain the same captured attempt through unknown outcomes and explicit retry. A second click or same-operation retry cannot allocate a new ID, select another row, borrow a changed revision or send edited values. Same ID with any different kind, target, actor, tenant, expected facts or canonical payload is a generic operation conflict/denial, with no side effect. An intentionally new save may use a new ID only after definitive committed operation proof, or a definitive rejection of the original attempt before any ambiguity arose. Once an attempt is unknown, a later retry/reconcile validation, stale, conflict or authorization rejection proves only that later call was rejected: it does not prove the delayed original cannot still commit. Keep the captured identity, unconfirmed state and replacement-submission/navigation guard until whole-operation terminal proof exists; do not allocate a replacement ID on such a rejection. No cancellation or terminal-failure framework is proposed, so some attempts may remain unresolved. Two deliberate identical creates with distinct IDs remain permitted and yield two different rows; equality of names, SKU or prices is never reconciliation evidence.

Minimum retention is in-memory for the mounted form, matching current booking patterns and ADR-B009 connected-web scope. Capture is not a durable offline queue. While pending/unknown, block destructive selection/navigation in the owned editor using its existing planned guard and keep a visible unconfirmed attempt. Full reload, tab closure or lost browser memory does not reconstruct the attempt; no claim of crash-safe draft recovery is made. Never interpret a reload or a list match as confirmation, and never automatically dispatch a replacement create after losing this identity. If persistence across browser restart is required, that is a separate material scope decision; do not silently add localStorage, IndexedDB, background replay or a server operation inbox. Same-actor recovery in another tab is supported only when that tab actually has the captured operation identity; other actors cannot adopt it.

## Contract: transaction, receipt, replay and reconciliation

Receipt identity is globally unique operationId, bound immutably to resolved tenant, actor, the closed operation enum, canonical request digest, captured target, original correlation and committed result. Store only operational metadata and minimal result (target ID, committed revision, committed-at/approval metadata where needed); no raw company PII, wording or prices in audit metadata. A digest is not an authorization capability and receipts are not browser-readable table rows.

For each v2 mutation: validate/authenticate; acquire the existing tenant advisory transaction lock first (same key/order used by current WorkRole and admin membership mutations); lock the actor's current tenant membership rows in deterministic order for share; recheck current role union; bind auth.uid() to actor; then inspect the receipt. Keep that authorization protection through commit. The shared tenant lock serializes ordinary admin revoke/re_role operations, and the membership lock protects the inspected membership against concurrent changes. Reuse current helpers rather than introducing new roles or trusting stale JWT role metadata. Do not promise to defeat a superuser or an out-of-contract privileged writer that intentionally bypasses authorization discipline.

If an exact committed receipt exists, return its historical committed outcome **before comparing the old expected revision with today's row**; never mutate, reapprove or append another audit. Current authorization must pass even for a historical replay. Cross-actor or cross-tenant operation ID reuse returns a generic denial and discloses no receipt fields. Lookup/constraint races must not become an existence oracle.

If no receipt exists, acquire/verify the target row with tenant predicate and FOR UPDATE, compare exact expected revision, execute the single mutation, write the fixed audit event and append the receipt in the **same transaction**. No success can precede all three writes. A receipt insert failure or injected audit failure rolls back the business write and revision change. The receipt uniqueness plus tenant lock serializes two concurrent same-ID creates. All existing-row operations verify target ownership in SQL after locks; the envelope ownership precheck is additional, not the race boundary.

For singleton creation, explicit expected absence must still hold. A concurrent singleton insert wins normally; the loser reports stale/conflict instead of taking an upsert update branch. Use uniqueness as the final check even against provisioning that did not take this producer's lock. Missing or foreign existing target is generic denial. A create candidate ID already used by a different operation cannot be repurposed into an update.

The non-mutating reconcile call takes the captured operation identity plus the same binding information/candidate needed to verify its digest, resolves current tenant/actor/capability, takes the same tenant/authority locks and returns either an authorized exact committed receipt or **unconfirmed**. It never inserts, writes an audit, changes a revision or executes a missing mutation. Missing receipt cannot prove the original request never reached the server: it may be delayed before lock acquisition or still arrive later. Timeout, connection failure, inaccessible receipt, absent receipt and lost response never imply business success or permission to retry under a new ID. Explicit retry dispatches only the same captured command; it either commits once, observes the receipt, or rejects that individual call. After prior ambiguity, even a definite rejection of the later call leaves the original operation unconfirmed unless whole-operation terminal proof is obtained. In particular, revoke → retry denied → restore does not retire the original identity: the original request delayed before its lock may still commit after restoration.

No receipt expiry/deletion, job, cleanup service or replay time window is introduced. Retain committed receipts with the tenant; receipt lifetime must outlive retry eligibility. A future retention policy must never expire the identity then allow its ambiguous create to become fresh. Reconciliation unavailability may leave an attempt indefinitely unconfirmed; communicate that limit honestly.

A committed result is historical, not a fresh read assertion. Return/bind its operationId, targetId and committedRevision. Independently refresh the current authorized row when displaying current saved data/approval. If that row changed since the receipt, show that the earlier operation completed and newer changes exist; do not copy its old fields into the editor or label them current. If the target was removed by privileged maintenance, do not recreate it from replay. If authorization has been revoked, return denial without historical details or reapplication. Replayed approval must never restore approval removed by a later save.

## Contract: stale facts and exact terms approval

Add write_revision to the authorized settings/pricing read DTOs, including archived pricing reads. Supply expected absence only on a successful null singleton read, never on read failure. Carry captured IDs/revisions through parsers, command validators, wrapper arguments and every action-state identity. A client-provided revision is a precondition, not an entitlement.

For company/terms update, pricing edit and archive/reactivate, compare the captured revision under the same SQL target lock through mutation/audit/receipt. Reject a stale request without touching row, approval, receipt or audit; retain the user's draft, refresh current facts and require a new deliberate submission. Lifecycle writes compare the full row revision: a stale archive must not silently archive somebody else's updated price. Same-value saves still advance revision; two tabs from one actor do not bypass comparison. No blind merge or client reread-then-write is sufficient.

Approval additionally carries the exact canonical persisted terms_text that the actor reviewed, the terms ID and current revision, including the approval-state revision. It cannot approve dirty unsaved text. SQL locks that same row and compares the wording byte-for-byte after the existing canonical trim semantics, plus revision and current approval state. If another actor saves different wording, or even saves then restores the same text, approval rejects stale. If another actor already approved the current wording, a new old-baseline approval rejects stale and preserves that actor/time; refresh shows the existing approval. **Proposed policy tightening requiring approval with this task:** a fresh approval requires that the exact reviewed revision is currently unapproved. A fresh attempt against an already-approved revision rejects and requires refresh, with no business write, receipt or audit event. This deliberately tightens current producer behavior, which permits a distinct deliberate reapproval to replace approver/time and append an audit; it is not claimed as unchanged historical policy. There is no already-current no-op success or invented no-op receipt. Exact committed replay is checked first and remains a historical completed approval, with no reapproval, timestamp change or duplicate audit. A rejection after an already-unknown attempt still does not establish that the original operation failed.

Every real terms text save, including an unchanged-text explicit save, still resets approved_at/by and renews revision. Saving never approves. A replay of an earlier save returns its old receipt and must not clear a later approval. A replay of an earlier approval must not approve later wording. The UI badge derives from current returned/read facts plus matching generation, not persistent justApproved=true overriding all later saves. This does not claim proof that the person read every word, change the sign-off permission, or amend ADR-B008 quote review/provenance policy.

## Risks, limits and completion boundary

The tenant advisory lock intentionally reuses existing pricing/membership ordering and may add low-volume settings contention; this is preferable to a second lock order. Verify it against current booking/lifecycle wrappers in review. Opaque revision triggers must run for every source UPDATE and be protected from ordinary spoofing. Enroll the new receipt table rather than hiding it in another schema to evade H4. Canonicalization and logo omission, the explicitly proposed unapproved-revision approval precondition and old RPC grant removal deserve first independent review attention.

In-memory attempt loss, indefinite reconciliation failure and later loss of permission are real limits, never false business success. This task supplies connected same-attempt recovery; it does not supply durable offline operation or cross-user takeover. Receipts identify past completion, not current approval or a current price. No automatic reconciliation polling/background service or retention policy is added. A full browser restart remains outside the claimed retry guarantee unless a later explicit scope decision extends it.

Implementation completion needs independently reviewed exact-head code, meaningful focused and required DB/RLS evidence (including concurrency and rollback), essential production-server browser evidence and current existing gates. Retain evidence counts/skips and one author-written Suggested Review Order. Preserve frozen sources and release_ready=false until the separately owned 35.7 presentation and release requirements are actually met. This prerequisite alone does not approve 35.6/35.7 parallel allocation, mark either story done, or authorize deployment/merge/push.
